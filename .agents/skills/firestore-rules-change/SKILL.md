# Firestore ルールの変更

アプリのデータを守っているのは `firestore.rules` だけです。画面やサービスの中で権限を確かめても、Firestore に直接リクエストを送れば回避できます。このリポジトリは公開されているので、ルールの穴は誰でも読めます。

コレクションごとの役割と今の権限、既知の穴は `docs/data-model.md` にあります。最初に読んでください。

## 1. 変更の前に

- 変えるコレクションを読み書きしているサービスを探します（`grep -rn "'<コレクション名>'" src/services`）。ルールを絞ると、そのサービスの書き込みが拒否されるかもしれません。サービスが書いているフィールドを一覧にしておきます。
- `firestore.rules` の冒頭の設計方針と、ヘルパー関数（`isAuthenticated`、`isOwner`、`isAdmin`）を確かめます。

## 2. ルールを書く

- 「ログインしていれば誰でも書ける」（`allow write: if isAuthenticated()`）を新しく増やさないでください。持ち主の確認と、書けるフィールドの限定を入れます。
- `write` を `create`・`update`・`delete` に分け、それぞれに必要な条件だけを書きます。
- よく使う書き方（フィールドの許可リスト、型と長さの検査、ハッシュ化した uid の照合、ほかのドキュメントの参照）は `references/rule-patterns.md` にあります。
- なぜその条件にしたかを、ルールのコメントに日本語で書きます。暫定のルールには、何を待っているかを書きます（既存の「暫定ルール」のコメントと同じ書き方）。

## 3. 確かめる

テストの仕組み（Emulator と `@firebase/rules-unit-testing`）は、まだリポジトリにありません。用意されるまでは、次の方法で確かめます。

1. ルールがコンパイルできるかを確かめます。

   ```bash
   firebase deploy --only firestore:rules --dry-run --project wadai-de-wadai-dev
   ```

   `--dry-run` はコンパイルだけを行い、何もデプロイしないので、承認なしで実行して構いません。エラーがあると、行と列を示して終了コード 1 で失敗します。Emulator の起動は、構文エラーがあっても成功するので、この確認には使えません。

2. 手順 1 で一覧にしたサービスの書き込みが、新しいルールで許可されるかを、ルールを読んで 1 つずつ確かめます。許可されないものがあれば、ルールかサービスのどちらを直すかを人に相談します。

3. 悪用の例（他人の uid で書く、許可していないフィールドを書く、未ログインで書く）が拒否されることを、ルールを読んで確かめます。

4. dev にデプロイして、画面で確かめます。手順は skill `deploy` の `references/rules-deploy.md` です（デプロイの前に人の承認を得てください）。

## 4. 文書を直す

同じ PR で `docs/data-model.md` を直します。

- コレクション一覧の「読み取り」「書き込み」の列
- 「既知の課題」：直した穴を消し、新しくわかった穴を足す

権限の流れ（代表者や管理者）が変わったときは、`docs/auth-and-roles.md` も直します。

## 結果の報告

変えたルール（コレクションと条件）、影響を受けるサービス、確かめた方法とその結果、まだ確かめていないこと（dev での画面確認など）を報告してください。
